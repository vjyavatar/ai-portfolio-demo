# Reviewed Opportunity Radar publishing

The user authorized publishing public research on Celesys and sending qualifying alerts to their explicitly supplied email. Website publication is implemented here; email is a separate, authenticated delivery capability. Installing Gmail does not establish that its send action is available or that delivery succeeded. Do not expose recipients, sender identities or email receipts in this public repository.

## Public surface

- `/ruralos/alerts/` renders accessible poster cards and complete evidence. Country filters include India and United States; an empty selection means no published qualifying evidence, not no opportunities.
- `/ruralos/alerts/feed.json` is a validated build-time public snapshot. No household information, anonymous writes, sending or transactions. No server routes changed.
- The RuralOS home checks this feed while visible and online, at most once a minute. This is not continuous research, push notification delivery or an instant-price feed.
- `data/ruralos-alerts.json` is the only editorial input. Source changes require a reviewed, tested release. No model can publish through a public endpoint.
- Source observations and publication/event dates are separate. Browser expiry checks run on page load, every30seconds and visibility changes; expired cards say `Needs recheck`. Without JavaScript, cards say dated snapshot and show the explicit review deadline. They disappear from the current home count. Alert pages/feed are excluded from service-worker offline caching and existing static responses require revalidation.

## Research and publication gate

1. Read latest remote main, `AGENTS.md` if present, this file and `docs/RURALOS-SPRINT.md`. Use an isolated checkout. Check existing catalogue and prior watch output for duplicates.
2. Verify material facts with authoritative primary sources. Keep a reasonably balanced India/NSE/BSE and US/SEC/exchange search, without forcing an alert for either country. No exhaustive-coverage claims. No new evidence means no new alert, commit, deployment or email.
3. Use a stable alert ID; increase `revision` only for a material, documented change. Never reset `checkedAt` or extend `reviewBy` without a fresh source check. A corrected/withdrawn thesis needs visible explanation. Do not remove risks to make a card look attractive.
4. Fill all common schema fields shown in the existing record: ID/revision/category, title/subject/country/market, publishedDate/eventDate, checkedAt/reviewBy, whatChanged/catalyst, facts/inferences/risks arrays, counterevidence/invalidation/nextStep/timing/price/limitations, and labelled HTTPS sources. Times need explicit zones. Dates must be real, and observation time cannot predate publication/event. Review period cannot exceed seven days. Max100 alerts and256KB. Trim older records only with an explicit retention decision.
5. `business_research`: corroborated operational change and a concrete lawful investigation, not speculative profits. An announcement or recruitment listing does not prove production, orders or outside purchasing. Clearly identify company targets.
6. `stock_research`: requires a `stock` object with every field in `ruralos_alerts.STOCK_FIELDS`: exchange, ticker, listingType (including ADR), quoteCurrency, reportingCurrency, observedQuoteAndTime (including delay), valuationBasis, financialPeriod, revenueAndProfit, cashFlow, balanceSheetDilutionLiquidity. Use INR with appropriate lakh/crore units for India, USD for US; source any conversion. Missing values must say `Not verified` with the gap explained. All stock cards remain research leads; never call incomplete information an actionable investment alert. No price targets, predicted returns or buy/sell instructions.
7. `travel_deal`: only after an actual live provider fare check. `travel` requires route, departureDate, optional returnDate, fareType, passengers, baggage, fees, cancellation, providerUrl, numeric total >0, ISO currency, liveAvailabilityChecked:true. Review window at most one hour. Include actual all-in total, dates, party assumptions, mandatory charges, restrictions, observation time and provider link. No stale advertised fare as available. No invented usual-price/discount/cheapest comparison. Recheck before any booking; never book or pay.
8. Every card separates verified observations from inference, shows risks/counterevidence, practical next action, expiry and the research disclaimer. Ensure the rendered poster agrees with written evidence. The HTML layout is the website poster; research notifications in chat may use generated portrait images only after fact verification.
9. Run `python ruralos_alerts.py` after any editorial change: malformed evidence fails the build before writing public files. Commit generated `ruralos/alerts/` pages/feed together with the source catalogue. Run meaningful schema/security/reliability tests: `PYTHONPATH=. python -m pytest tests/test_ruralos.py tests/test_ruralos_live.py tests/test_ruralos_alerts.py -q`, `npm run build`. If UI changes, run TypeScript, `node tools/check-ruralos-ui.mjs` and the preserved `python tools/build-ruralos.py` first; the latter also builds alerts. No weakening tests.
10. Re-fetch main before publishing; use exact latest parent and non-forced update. Check Render service `srv-d690qd0gjchc73det890`, confirmed workspace `tea-d690ma14tr6s73cdsvn0`. Do not deploy concurrently. Do not duplicate an automatic release. Follow existing public-clone deployment caveat in sprint log. Verify live commit, HTML, JSON evidence/revision and sources after release; record exact commits, checks and remaining risks.

## Email delivery gate and duplicate prevention

- Recipient is held in the user's private watch instructions, never this public data file. Only that recipient is authorized; no bulk mailing or contacting companies.
- Before enabling email in the existing watch, successfully call a harmless Gmail read action and verify the sending account and exact recipient. If tools/permissions are absent, stop the email step, state the precise missing access and continue website work. Do not substitute another application's SMTP credentials.
- For each qualified alert/revision, search sent mail for the exact subject marker `[Celesys alert: ID rREVISION]`. If already sent, skip. After an ambiguous send result, search again before retrying. Never blindly retry a sending operation.
- Send a readable poster-style summary plus complete facts, observation/publication/event times, price/valuation or fare details, risks, counterevidence, invalidation and sources. Link to the verified live card. HTML only if the Gmail tool supports it; otherwise structured plain text with a poster-page link. Never claim attachment/image support unless confirmed.
- Record the provider-confirmed send result privately. `Sent` does not prove inbox delivery/read receipt. If a send fails, report failure without claiming email success. Public UI has no per-recipient delivery status and no open subscription form.
- Update the existing Opportunity Radar watch rather than creating another one. Website/email authorization does not authorize changing its quality gates, frequency, stock transactions or paid subscriptions.

## Remaining limits

No live fare/stock data subscription, email worker, phone push, publicly writable CMS or guaranteed continuous research. The app's family reminders and authenticated tracking are separate. The initial real card is a business research lead, not a recommendation to buy a security. Hindi/Telugu controls exist; long research evidence is currently English. Physical-device accessibility and rural comprehension remain unverified.
