# r63.71 Deploy Guide

This is a **foundation-only** release. The web app behaves identically
to r63.70 from a user's perspective. You're laying the database and
ingestion pipeline that the next 3 revisions will build on.

There are 3 phases:

1. **Render deploy** — push the code, set env vars, restart. ~10 minutes.
2. **DB migration** — run once against Neon. ~30 seconds.
3. **Backfill** — run from your laptop, leave running 4–6 hours. One-time.

Once all three are done, the database has 8 quarters of 13F holdings
data and you're unblocked for r63.72 (scoring engine).

---

## Phase 1 — Render deploy

1. Unzip and push to your Render-connected repo as usual:
   ```
   unzip celesys_v4_r63.71.zip
   cd celesys_v4_FINAL_DEPLOY
   # commit + push to your Render-tracked branch
   ```

2. In the Render dashboard for the Celesys service, add these
   environment variables:

   | Key                  | Value                                                                 |
   | -------------------- | --------------------------------------------------------------------- |
   | `NEON_DATABASE_URL`  | Your Neon **pooled** connection string. Must include `?sslmode=require`. |
   | `OPENFIGI_API_KEY`   | Your registered OpenFIGI key.                                          |
   | `SEC_USER_AGENT`     | (optional) `Celesys Research vjyavatar@gmail.com` — already the default. |

   The pooled connection string from Neon looks like:
   `postgresql://user:pass@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require`

   Use the **pooled** endpoint (with `-pooler` in the host), not the
   direct one. Neon scales compute to zero — pooled is what handles
   that gracefully.

3. Trigger a deploy. Render will rebuild with the new
   `psycopg[binary,pool]`, `httpx`, `tenacity`, `lxml` dependencies.
   Build time will be ~2 minutes longer than usual the first time.

4. After deploy completes, check the service logs. You should see:
   ```
   🗄️  Positioning DB (Neon): connected
   ```
   If you see `NOT connected` instead, the env var is wrong or
   firewall is blocking — check the reason in the log line.

5. Hit `https://celesys.ai/health` in a browser. You should see a
   new field at the bottom:
   ```
   "positioning_db": {"ok": true}
   ```

## Phase 2 — Apply schema to Neon (one time)

This creates the 6 tables. Idempotent — safe to re-run.

**Option A — from Render shell (easiest):**

In Render dashboard, open the Shell tab on the Celesys service and run:
```
python db/migrations/001_initial.py
```

Expected output:
```
Applying schema from: /opt/render/project/src/db/schema.sql
Schema size: ~7,300 chars
Connecting to: ep-xxx-pooler.us-east-2.aws.neon.tech
OK — schema applied in 1.42s
Verified 6 tables present: ['cusip_ticker_map', 'filers', 'filings', 'holdings', 'ingestion_log', 'mapping_overrides']
```

**Option B — from your laptop:**

```
cd celesys_v4_FINAL_DEPLOY
pip install 'psycopg[binary]>=3.1'
export NEON_DATABASE_URL='postgresql://...your...connection...string...'
python db/migrations/001_initial.py
```

Verify in the Neon console (Tables view) that all 6 tables exist.

## Phase 3 — Backfill 8 quarters of 13F filings

**Run this from your laptop, not Render.** Render will kill long jobs.

```
cd celesys_v4_FINAL_DEPLOY
pip install -r requirements.txt

export NEON_DATABASE_URL='postgresql://...your...connection...string...'
export OPENFIGI_API_KEY='your-figi-key-here'
export SEC_USER_AGENT='Celesys Research vjyavatar@gmail.com'

# Smoke test first — pull just 5 filings to confirm everything wires up:
python tools/backfill_13f.py --quarters 1 --max-filings 5

# Real run — leave overnight:
python tools/backfill_13f.py --quarters 8
```

What you'll see during the smoke test:
```
DB health: OK
Backfill plan: [(2024, 2), (2024, 3), (2024, 4), (2025, 1), (2025, 2), (2025, 3), (2025, 4), (2026, 1)]

=== Filing-quarter 2024Q2 ===
  index: 5,247 13F-HR entries
  ...progress: 5 filings · 1,234 holdings · 1,180 resolved
hit --max-filings cap, stopping
```

What you'll see during the real run, every 25 filings:
```
  progress: 1,250 filings · 187,432 holdings · 178,901 resolved · 0.7 filings/sec
```

If you Ctrl-C, just re-run the same command. Already-ingested filings
skip via the `accession_no` UNIQUE constraint.

**Expected end state after a full 8-quarter run:**
- ~25,000–35,000 filings in `filings`
- ~5–15 million rows in `holdings`
- ~30,000–50,000 unique CUSIPs in `cusip_ticker_map`
- ~92–96% of CUSIPs resolved to tickers (the rest are foreign,
  delisted, or odd-lot securities — expected residue)

## Verifying the data

Spot-check a single ticker's positioning history:

```sql
SELECT period_of_report,
       COUNT(DISTINCT cik)            AS filers_holding,
       SUM(value_usd)::bigint         AS total_value_usd,
       SUM(shares)::bigint            AS total_shares
FROM holdings
WHERE ticker = 'NVDA'
GROUP BY period_of_report
ORDER BY period_of_report DESC;
```

You should see one row per quarter showing how many institutional
filers held NVDA and the aggregate value/share count.

If everything looks right, you're ready for r63.72 (scoring engine).

## What's NOT in this release

By design:

- No `/api/positioning-*` endpoints
- No Decide tab UI for the scanner
- No scoring or ranking logic
- No frontend wiring whatsoever

All of that comes in subsequent revisions. Foundation must be stable
first.

---

## Rollback

If anything goes wrong, the entire r63.71 layer is **opt-in via env
vars**. To roll back, just delete `NEON_DATABASE_URL` from Render env
and the app reverts to r63.70 behavior — `positioning_db.ok` becomes
false in `/health`, the startup log says "NOT connected", and nothing
else is affected. The Neon database itself is untouched.

To fully roll back code-wise: redeploy `celesys_v4_r63.70.zip`.
