# r63.71.5 — Storage cleanup + focused backfill

This release addresses two issues from the previous run:

1. **Storage cap hit.** Free-tier Neon's 512 MB ceiling stopped the
   backfill at ~7,500 filings with the bulk of inserts failing.
2. **Period-of-report bug.** The old heuristic snapped all filings to
   2024-06-30 — single quarter of data, no Q-over-Q delta possible.

This revision ships three things to recover:

- A cleanup script that trims the DB to the **top 2,000 filers by AUM**,
  freeing 60–80% of the storage
- An accurate `periodOfReport` extractor that reads the cover page XML
  instead of guessing from filing date
- A `--top-filers N` flag for the backfill to skip non-whitelisted CIKs
  before any DB or network work

After running these three steps, the DB will hold 8 quarters of focused
top-filer data — sharper signal, well within free-tier storage, and
ready for r63.72 scoring.

## Step 2 — Run the cleanup (interactive, ~1–2 minutes)

Set env vars and run the cleanup script:

```powershell
$env:NEON_DATABASE_URL = "postgresql://...your...neon..."
python tools\cleanup_db.py --top-filers 2000
```

The script will:

1. Show you the current state (filer/filing/holding counts, storage used)
2. Identify the top 2,000 filers by aggregate AUM from existing data
3. Show you exactly what will be deleted (counts + percentages)
4. Ask `Proceed with deletion? [y/N]:` — type `y` to confirm
5. Execute deletion inside a transaction (rolls back on any error)
6. Run `VACUUM ANALYZE` to release space

## Step 4 — Verify in Neon

After backfill completes, run this to confirm the period-of-report fix:

```sql
SELECT period_of_report,
       COUNT(*) AS filings,
       COUNT(DISTINCT cik) AS unique_filers,
       ROUND(SUM(holdings_count)::numeric / 1e6, 2) AS holdings_millions
FROM filings
GROUP BY period_of_report
ORDER BY period_of_report DESC;
```

Expected: 8 rows, one per quarter, each with ~2,000 unique filers and
similar holdings counts. If you still see only one row with most data,
the period parser had an issue — let me know.

Then run the top-15 sanity check:

```sql
SELECT ticker, issuer_name,
       COUNT(DISTINCT cik) AS filers,
       ROUND(SUM(value_usd) / 1e9, 1) AS aum_billions,
       COUNT(DISTINCT period_of_report) AS quarters_present
FROM holdings
WHERE ticker IS NOT NULL
GROUP BY ticker, issuer_name
ORDER BY aum_billions DESC
LIMIT 15;
```

Each top-15 ticker should now show `quarters_present = 8` — meaning
those names appear in every one of the 8 quarters in the database.
That's what unblocks Q-over-Q delta math in r63.72.
